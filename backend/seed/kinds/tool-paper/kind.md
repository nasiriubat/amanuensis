# Tool paper

A paper whose main contribution is a software tool, system or platform. It argues that
the tool solves a real problem for identifiable users, explains the design decisions
that make it work, and shows evidence that it does.

## What reviewers expect

- A clearly stated problem with named users, and why existing tools fall short for them.
- The contribution stated as capabilities the tool adds, not as a feature list.
- Architecture and design decisions with reasons. Alternatives that were rejected and why.
- Some evidence: a user study, a case study, a benchmark, an expert evaluation or a
  well-argued demonstration on realistic inputs. The kind of evidence must match the
  claim.
- Availability: where the tool can be found, licence, how to run it.
- Honest limitations and threats to validity.

## Common reasons for rejection

- "This is engineering, not research." The paper describes what was built but never
  states what question it answers or what is new compared to prior tools.
- Related work lists tools without positioning against them.
- Claims outrun evidence: "improves productivity" with no measurement.
- No users or use case named. The tool exists in a vacuum.
- Evaluation on toy inputs the authors made themselves.
- Screenshots in place of an explanation of how the tool works.

## Framing moves that work

- Open with the concrete pain, in one paragraph, with a scenario.
- State two to four contributions as verbs: "We design ...", "We implement ...", "We
  evaluate ... with ... and find ...".
- Give the reader a running example that returns in the design and evaluation sections.
- Compare against the closest two or three tools in a small table.
